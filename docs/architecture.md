# Архитектура PRTDS — срез 1 (сквозной коммерческий путь)

Статус документа: внутренняя инженерная документация. Редакция от 08.11.2026.
Источник требований — [`prtds-concept-v2.md`](prtds-concept-v2.md), в первую
очередь §06, §07, §10, §13, §14, §15.

---

## 1. Что именно построено

Один сквозной путь, доведённый до подтверждённого экономического результата:

```
поиск → карточка → WhatsApp / заявка → CRM-статус → подтверждённый результат → основание комиссии
```

Это **не** витрина и не прототип интерфейса: путь опирается на общий доменный
контракт (§13.1), поэтому к нему можно подключать реальный каталог и реальные
договоры, а следующие вертикали будут использовать те же сущности вместо
создания своих «мини-платформ».

### Контур среза

| Внутри среза | Вне среза (следующие фазы) |
| --- | --- |
| Каталог: категории, компании, филиалы, товары/услуги, каналы, источники | Лояльность, баллы, уровни, кэшбэк-бюджеты как отдельная подсистема |
| Поиск + фильтры + рекламный блок | Бронирование и расписания |
| Карточка компании, эффективная цена (отображение) | Корзины и платежи |
| События воронки, идемпотентность, UTM-атрибуция | B2B-закупки, тендеры, логистика |
| Заявки, согласие, CRM-статусы | ИИ-ответы и ассистенты |
| Договоры, правила комиссии, ликвидации, CM | Новостной и событийный контент |

Эффективная цена и правила лояльности реализованы только как **отображение**
(`compute_effective_price`) — деньги списываются и начисляются в модуле commerce.

## 2. Архитектурные решения

| # | Решение | Обоснование |
| --- | --- | --- |
| A1 | Modular monolith: один процесс FastAPI отдаёт и API, и фронтенд | §13.1 требует общих сущностей и ясных границ модулей, а не микросервисов. Один процесс = одна транзакционная граница для факта «событие → ликвидация»; расщепление на сервисы появилось бы раньше, чем появились бы данные |
| A2 | Модули без HTTP (`app/modules/*`), HTTP-адаптеры тонкие (`app/api/*`) | Бизнес-правила (капы, CM, идемпотентность) проверяются тестами без веба и переносятся в любой транспорт |
| A3 | Frontend — vanilla ES Modules, без сборщика | Совпадает с техпаспортом (HTML/CSS/JS ES Modules + Worker) и с рынком: 96,9% мобильного интернета в Парагвае, слабые устройства. Механически переносится в Cloudflare Worker |
| A4 | Относительные URL везде | Один origin для страниц и API: работает за прокси превью, за nginx и за Worker без переделки |
| A5 | Деньги — целые гуарани (`BigInteger`), ставки — базисные пункты (`Integer`, 10 000 = 100%) | PYG не имеет дробных единиц (§02). BPS исключает накопление ошибки округления при капах и процентах; округление — half-up одной функцией `apply_bps` |
| A6 | Enum'ы — VARCHAR + CHECK (`native_enum=False`), без native ENUM | Переносимость SQLite ↔ PostgreSQL и миграции без ALTER TYPE; словарь событий живёт в коде (`core/funnel.py`), значения — в данных |
| A7 | Все факты каталога несут provenance: `source_id`, `observed_at`, `verification_level`, `valid_until`, `updated_by`, `is_stale` | §13.4: у каждого факта — источник, время, уровень подтверждения, владелец, признак устаревания |
| A8 | Словарь категорий, синонимы и фразы-возможности филиалов — **данные**, а не код | Новые категории добавляются через API без деплоя (решение команды: «универсальный каталог с возможностью задать категории») |
| A9 | Публичный ingest событий ограничен словарём «осведомлённости» | Коммерческие факты (`sale_confirmed`, `settlement_created`) нельзя создать из браузера: 422. Защита от подделки комиссий |
| A10 | Платная позиция — отдельный помеченный массив, органика — отдельно | §13.4: рекламное место не выдаётся за объективно лучшее предложение; продвигаемая карточка не занимает органический слот |
| A11 | Согласие регистрируется до передачи контакта | §13.4 + §07: заявка без `consent.granted` → 403, контакт не передаётся продавцу |
| A12 | Идентификатор обращения (`ref_code`) создаётся уже на клике WhatsApp | Диалог в мессенджере ссылается на PRTDS, а не наоборот: событие `whatsapp_click` становится атрибутируемым фактом с ссылкой, которую партнёр видит в переписке |
| A13 | Демо-токены кабинетов, никаких секретов в репозитории | §13.4: пароли, токены и приватные ключи не хранятся в коде и документах. В production — Google Identity Services |
| A14 | Версионированные миграции Alembic + идемпотентный сид | §13.4: разработка не обгоняет миграции; сид безопасен для повторного запуска и полного сброса |

```
│   ├── db.py         Base, engine (SQLite PRAGMAs / PG pool_pre_ping), SessionLocal, init_dev_database
│   ├── ids.py        utcnow, new_id(kind), ref_code, stable_hash, hash_pii
│   ├── money.py      apply_bps (half-up), format_pyg, EffectivePrice, ContributionMargin
│   ├── text.py       fold() — NFKD-свёртка акцентов, contains()
│   ├── funnel.py     EventType, словарь FUNNEL (prove / not_prove_es / stage), NOT_EQUIVALENT_ES
│   └── security.py   hash_token, token_matches (constant-time)
├── domain/
│   ├── models.py     19 таблиц общего ядра
│   └── schemas.py    Pydantic DTO входа/выхода
├── modules/
│   ├── catalog.py    дерево категорий, поиск, фасеты, карточка, эффективная цена, reindex
│   ├── funnel.py     запись событий, идемпотентность, согласие, атрибуция, сводки
│   ├── leads.py      WhatsApp/звонок-ссылки, создание и CRM-жизненный цикл заявки
│   └── commerce.py   договоры, правила комиссии, ликвидации, экономика, алерты
├── api/
│   ├── deps.py       сессия БД, клиентский контекст, токены партнёра/админа
│   ├── public.py     человек: поиск, карточка, события осведомлённости, заявка
│   ├── partner.py    commerce: сверка заявок, продажа, ликвидации, дашборд
│   └── admin.py      каталог: таксономия, публикация, правила, источники, аудит
└── seed/             демо-датасет + загрузчик (сброс/восстановление)
```

Правило зависимостей: `api → modules → domain/core`. Модули не импортируют друг
друга по кругу: `commerce` использует `funnel` для записи событий, `leads`
использует `funnel` и `catalog`; `catalog` не знает о комиссиях.

## 4. Доменная модель

Общие сущности §13.1 реализованы буквально, с сохранением различий между ними
(Company ↔ LegalEntity ↔ Brand ↔ Branch — **не** одно и то же).

| Группа | Таблицы | Роль |
| --- | --- | --- |
| Справочники | `sources`, `legal_entities`, `brands`, `categories`, `company_categories` | Происхождение фактов; реестр лиц отдельный от публикаций; таксономия как данные |
| Каталог | `companies`, `branches`, `contacts`, `offers` | Публикационная единица, точка присутствия, канал, товар/услуга с ценой и доступностью |
| Правила | `benefit_rules` | Условия скидок/кэшбэка (партнёрские, платформенные, банковские) — данные, а не код |
| Воронка | `funnel_events`, `consents` | Append-only журнал фактов; согласия с целью, текстом, каналом и сроком |
| Сделки | `leads`, `lead_attributions` | Обращение человека и основание «кто привёл» |
| Экономика | `contracts`, `commission_rules`, `settlements`, `partner_users` | Договор, правило расчёта, ликвидация, доступ кабинета |

Ключевые связи:

```
LegalEntity ──┐
Brand ────────┼── Company ──┬── Category (M:N через company_categories)
              │             ├── Branch ──┬── Contact (канал)
              │             │            └── Offer ── BenefitRule (M:N)
              │             ├── Contract ── CommissionRule
              │             └── Lead ──┬── LeadAttribution
              │                        ├── FunnelEvent (1:N, по стадиям)
Source ───────┴──────────> каждый факт   └── Settlement (1:1 на событие-основание)
```

Каждая таблица фактов несёт `source_id` + `observed_at` + `verification_level`
+ `valid_until` + `updated_by` (`FactMixin`) и вычисляемый `is_stale`.

### Идентификаторы

`new_id(kind)` — префикс + время-сортируемая строка (`cmp_`, `brn_`, `ld_`, `ev_`,
`stl_`, …): сортируемы без запроса, не раскрывают счётчик публично. Для человека —
`ref_code` формата `PRTDS-2026-000123` (год + последовательность) и короткий
`WA-YYMM-XXXXXX` для обращения в мессенджере.

## 5. Воронка событий (§07)

Событие — факт, а не «активность». Каждое событие несёт: тип, стадию, актора,
субъект (company/branch/offer/lead), канал, источник, кампанию, UTM, сумму,
ключ идемпотентности и согласие.

| Событие | Стадия | Комиссионное | Что НЕ доказывает |
| --- | --- | --- | --- |
| `view` | awareness | нет | интерес или намерение |
| `search_result` | awareness | нет | качество выдачи или наличие товара |
| `card_open` | interest | нет | контакт с продавцом |
| `whatsapp_click` / `call_click` | interest | нет | доставку сообщения, диалог, продажу |
| `lead_submitted` | contact | нет (кроме отдельного договора) | принятие заявки продавцом |
| `lead_accepted` / `booking_confirmed` | conversion | да (по договору) | факт оплаты |
| `sale_confirmed` / `receipt_matched` | conversion | **да** | повторную покупку или лояльность |
| `repeat_purchase` | retention | да | ценность клиента в горизонте года |
| `reward_earned` / `reward_redeemed` | retention | нет | экономическую эффективность программы |
| `lead_disputed` / `lead_cancelled` | exception | нет | корректность исходной атрибуции |
| `settlement_created` | settlement | служебное | выплату (выплата — отдельный статус) |

### Идемпотентность

Ключ строится на сервере (`build_idempotency_key`) и зависит от стадии:

- awareness / interest / contact — бакет **5 минут** (обновление страницы не
  размножает события);
- conversion / retention — бакет **сутки** + идентификаторы продавца и заявки
  (одно подтверждение продажи в день — один факт);
- явный `idempotency_key` клиента имеет приоритет.

Подтверждение продажи дополнительно выводит ключ из
`(event_type, lead, partner, сумма, реквизит чека, день)`: повтор того же чека
схлопывается в то же событие и ту же ликвидацию, а **другой чек** в тот же день —
это другая операция (`repeat_purchase`), и она создаёт новую ликвидацию.

Ликвидация идемпотентна по `stable_hash("settlement", event.id)`: одно событие
→ не более одной ликвидации.

### Атрибуция

Окно по умолчанию 7 дней (`attribution_window_days`). Приоритет метода:

1. `direct` — заявка ссылается на конкретный источник/кампанию;
2. `utm` — последний значимый touch с campaign/UTM в пределах окна;
3. `session` — события той же клиентской сессии;
4. `none` — вне окна (атрибуция записывается как спорная, комиссия не начисляется
   без договора на такой случай).

## 6. Экономика (§10)

Выручка PRTDS = комиссия / сервисный сбор, **не** оборот магазина.

```
commission = apply_bps(basis_amount, rate_bps)          # basis = сумма подтверждённой операции
             − platform_funded_discount                  # скидка за счёт платформы
             → cap per event (если задан)
             → cap per period (остаток лимита договора)
             → floor/minimum (если задан)

contribution_margin = commission
                      + other_confirmed_funding
                      − platform_funded_discount
                      − direct_costs (AI/платежи/поддержка/доставка/затраты партнёра)

правило: contribution_margin > 0 для каждой завершённой операции
```

Порядок разрешения правила (детерминированный, без угадывания):

```
правило договора → правило по компании → правило по категории → глобальное правило
```

`repeat_purchase` наследует правило `sale_confirmed`, если отдельного правила нет
(повторная покупка — та же подтверждённая продажа).

### Статусы ликвидаций

| Статус | Смысл | Влияет на выручку? |
| --- | --- | --- |
| `pending` | ждёт сверки с партнёром | да (начислено) |
| `approved` | сверено партнёром | да |
| `paid` | выплачено/зачтено | да |
| `flagged_negative_cm` | CM ≤ 0: операция экономически нецелесообразна | **нет** (видна в отдельном поле `flagged_negative_margin_pyg`) |
| `no_contract_basis` | нет договора или применимого правила | нет (но оборот учтён как GMV) |
| `disputed` | оспаривается | нет |
| `void` | аннулирована | нет |

### Демонстрационные сценарии в датасете

| Компания | Правило | Что показывает |
| --- | --- | --- |
| `nails-mburucuya` | 7% (beauty) − 4 000 G затрат, капа периода 2 000 000 G | рабочая экономика: 180 000 → 12 600 → CM 8 600 |
| `parrilla-yvoty` | договора **нет** | продажа есть, комиссии нет: `no_contract_basis` |
| `almacen-dona-nidia` | 1% + 50 000 G затрат | отрицательный CM: `flagged_negative_cm` |
| `supermercado-kaaguy` | 3%, кап 120 000 G на событие | срабатывание капа |
| `rentcar-terere` | 5%, минимум 200 000 G | операция ниже минимума → 0 комиссии |
| `estudio-contable-aty`, `clinica-mborayhu` | канал без WhatsApp | отказ в WhatsApp-ссылке и список альтернативных каналов |
| `bodega-mboriahu-staging`, `taller-registro-maestro` | статусы staging/draft | неопубликованные карточки недоступны публично |

## 7. Каталог, публикация и качество данных

### Pipeline публикации (§13.4)

```
draft → staging → validation → moderation → published
                          ↘ rejected / archived
```

Незаконный переход (например, `draft → published`) — HTTP 422 с перечнем
допустимых шагов. Публичные эндпоинты и поиск читают **только** `published`.

`/api/meta/status` и `/salud` показывают разницу контуров честно: сколько
юридических лиц в реестре, сколько компаний в каталоге и сколько карточек
опубликовано. Это прямое следствие §15: «юридические лица ≠ опубликованные бизнесы».

### Поиск

Текущая реализация — переносимая (работает и на SQLite, и на PostgreSQL):

1. Нормализованный поисковый текст (`search_text_norm`) строится при записи:
   NFKD-свёртка акцентов, название, описание, категории + синонимы, баррио,
   каналы, фразы-возможности филиалов (`24 horas`, `delivery`, `retiro en local`),
   названия товаров.
2. Запрос сворачивается тем же `fold()`, бьётся на токены; совпадение = все токены
   найдены (AND) либо совпала фраза/название.
3. Релевантность: совпадение названия > совпадение категории > промо-статус >
   свежесть; сортировки `relevance | name | recent | price_asc`.
4. Спонсорские карточки выносятся в отдельный блок `sponsored` с меткой `Publicidad`
   и пояснением; в органику не подмешиваются.
5. Показ выдачи фиксируется как `search_result` (осведомлённость, не продажа).

`POST /api/admin/reindex` перестраивает нормализованный текст (идемпотентно).

### Production-путь поиска (миграция на PostgreSQL)

| Сейчас | В production |
| --- | --- |
| `fold()` в Python + LIKE по токенам | `unaccent()` + `to_tsvector('spanish', …)` + GIN-индекс |
| Совпадение токенов в Python | `websearch_to_tsquery`, `ts_rank_cd` для ранжирования |
| — | `pg_trgm` (GIN) для опечаток и частичных совпадений |
| Координаты как `Numeric` | PostGIS `geography` + GiST, сортировка «рядом со мной» |
| Синонимы в JSON колонке | `synonym`/`thesaurus`-словарь PostgreSQL + тот же JSON как источник |

Известное ограничение текущей версии: квалификаторы цены (`celular barato`) не
обрабатываются — в словаре нет лексемы «barato». Production-решение: расширение
словаря запросов (данные) + `sort=price_asc`, а не эвристика в коде.

## 8. API-поверхность

| Группа | Префикс | Аутентификация | Назначение |
| --- | --- | --- | --- |
| Public | `/api/*` | клиентский контекст (заголовки сессии/актора) | человек: поиск, карточка, события осведомлённости, заявка, статус своей заявки |
| Partner | `/api/partner/*` | `X-Partner-Token` | commerce: заявки, переходы статусов, подтверждение продаж, ликвидации, дашборд |
| Admin | `/api/admin/*` | `X-Admin-Token` | каталог и аудит: таксономия, публикация, правила, договоры, источники, журнал событий, статистика |

Ошибки: 422 с перечнем полей (валидация), 403 (нет согласия / чужая компания),
404 (не опубликовано / нет канала), 500 — единый честный ответ
`Nada fue confirmado.` (никакой факт не записан при падении).

## 9. Фронтенд

Vanilla ES Modules, без сборки, mobile-first, es-PY:

| Страница | Файлы | Задача экрана |
| --- | --- | --- |
| `/` | `index.html`, `assets/js/search.js` | найти и открыть карточку: категории, фильтры, рекламный блок, пагинация, синхронизация с URL |
| `/empresa/{slug}` | `company.html`, `assets/js/company.js` | решить и связаться: филиалы, часы «сегодня», товары с разбором цены, WhatsApp/звонок с предзаполненным сообщением, форма заявки с явным согласием, свежесть и источник каждого факта |
| `/solicitud/{ref}` | `lead.html`, `assets/js/lead.js` | знать, что происходит с обращением: таймлайн статусов, без контактных данных и без денег |
| `/socio` | `partner.html`, `assets/js/partner.js` | сверить и подтвердить: дашборд (GMV ≠ выручка), заявки с переходами, подтверждение продажи, ликвидации |
| `/admin` | `admin.html`, `assets/js/admin.js` | управлять каталогом: таксономия с синонимами, pipeline публикации, переиндексация, ликвидации, журнал событий |
| `/salud` | `status.html`, `assets/js/status.js` | честно показать состояние: метрики каталога и экономики, словарь воронки, что ожидает проверки |

Общие модули: `api.js` (относительные URL, токены, `ApiError`), `format.js`
(PYG, даты, словари статусов, бейджи, экранирование HTML), `tracking.js`
(fire-and-forget события + UTM из адреса).

Принципы §13.4 в интерфейсе: реклама помечена; каждый факт показывает источник и
срок годности; согласие запрашивается до передачи контакта; деньги отображаются
как `G. 1.250.000` без дробных единиц; часовая зона America/Asuncion.

### 9.1 Языки интерфейса (ES / RU / EN)

Решение: продукт остаётся **Spanish-first** (§02) — испанский язык по умолчанию и
язык для пользователя в Парагвае. Русский и английский добавлены как языки
просмотра для команды и партнёров, а не как языки продукта.

Технически перевод не размазан по шаблонам экранов, а применяется поверх уже
отрисованного DOM (`assets/js/i18n.js`):

* словарь — соответствие «испанский оригинал → перевод»
  (`frontend/i18n/translations.jsonl` → генерируемый `assets/js/i18n-dict.js`);
* отдельные шаблоны для строк с подстановками (счётчики, свежесть данных, даты с
  испанскими месяцами);
* `MutationObserver` переводит то, что экраны дорисовывают после загрузки,
  поэтому перевод не зависит от порядка рендеров;
* оригиналы текстовых узлов хранятся в `WeakMap`, поэтому переключение языков
  обратимо и не «портит» строки повторным переводом.

Почему так, а не через ключи в каждом шаблоне: экраны уже работали и были
проверены, а словарь по оригиналу переводит и статику, и то, что пришло из API,
без переписывания 1,5 тысяч строк. Цена решения — пропуск перевода незаметен
глазами, поэтому он измеряется: `scripts/check_i18n_coverage.js` рендерит
страницы в DOM и возвращает код 1, если остались непереведённые испанские строки
вне списка намеренно непереводимого.

Не переводятся: названия компаний, брендов и баррио, адреса, телефоны, SKU,
номера обращений, коды событий и статусов — это данные продавцов и идентификаторы.
В production словарь просто не будет содержать контент реальных продавцов, так что
поведение останется тем же: текст платформы переведён, данные продавца — на языке
продавца.

### 9.2 Офлайн-сборка демо

`scripts/build_offline_demo.py` записывает живые ответы API и собирает страницы в
самодостаточный HTML (`docs/demo/`): стили и скрипты встроены, сетевой слой
заменён записанными данными. Нужно это потому, что стенд разработки доступен не
всегда (превью песочницы отдаёт 403 без служебного токена, GitHub Pages требует
прав владельца), а показать интерфейс команде надо.

Тонкости, которые учтены в сборщике:

* ES-модули не работают с `file://`, поэтому модули склеиваются в один classic-
  скрипт; он переносится в конец `<body>` (встроенный classic-скрипт, в отличие
  от модуля, не откладывается и выполнился бы до появления DOM);
* переопределения `pathParam`/`queryParam` ставятся после общих модулей —
  объявления функций всплывают, и побеждает последнее;
* каждая страница несёт только нужную ей часть записанных ответов;
* для `/api/search` ключи нормализуются к порядку параметров браузера, а при
  отсутствии точной записи параметры отбрасываются по очереди, чтобы фильтр
  показывал ближайший записанный результат вместо пустоты.

Сборка проверяется выполнением страниц в DOM (jsdom): 0 ошибок консоли, данные
отрисованы, покрытие перевода полное для RU и EN.

## 11. Тестирование

`pytest` + `httpx` TestClient на временной SQLite-базе, датасет пересоздаётся
перед каждым тестом (`autouse`), поэтому тесты независимы и детерминированы.

Три файла покрывают три группы правил:

- `test_catalog.py` — публикация только из `published`, staging недоступен,
  pipeline и его запреты, поиск (акценты, токены, синонимы, товары), фильтры,
  фасеты, рекламный блок отдельно, дерево категорий со счётчиками, эффективная
  цена с разделением гарантированной и условной выгоды, свежесть, переиндексация;
- `test_funnel.py` — публичный ingest не принимает коммерческие факты, дедупликация,
  `card_open` один раз на визит, WhatsApp-ссылка как попытка со ссылкой, отказ при
  отсутствии канала, согласие обязательно, идемпотентность заявки, атрибуция по
  последнему значимому touch, словарь воронки и метаданные рынка;
- `test_commerce.py` — полный путь до комиссии, GMV ≠ выручка, продажа без
  договора = 0, идемпотентность повторного подтверждения, два чека = две операции,
  отрицательный CM помечен и виден, капы (событие и период), минимум, изоляция
  партнёров, спор ликвидаций, сверка счётчиков воронки с журналом.

Правило команды: «зелёные тесты модели ≠ работающий production-сервис» (§15),
поэтому отдельный контур — живой HTTP-прогон (`scripts/dev.sh` + curl-сценарий в
README) и чек-лист Фазы 0 для production.

## 12. Развёртывание в production

Целевой контур из техпаспорта (§12 концепции):

```
Cloudflare Worker (prtds-web)  →  статика + edge-логика поиска
Render: prtds-auth, prtds-catalog-api  →  FastAPI
Neon PostgreSQL 18.6 + PostGIS (prtds-commerce)  →  система записи
GitHub Actions  →  миграции, тесты, деплой
```

Порядок действий:

1. **Фаза 0 — read-only аудит** (см. [`phase0-inventory-checklist.md`](phase0-inventory-checklist.md)):
   что реально существует в Neon (247 таблиц / 109 представлений), Render,
   Worker и ветке `prtds-engineering-v1` репозитория `sa-platform`.
2. Схема этого репозитория накатывается **отдельными миграциями поверх**
   существующей, без переименования и удаления чужих объектов; при конфликте имён
   — префикс `prtds_v2_` или отдельная схема PostgreSQL.
3. Поиск переводится на `unaccent` + `tsvector` + `pg_trgm`, гео — на PostGIS.
4. Фронтенд переносится в Worker как статические ассеты (модули не требуют
   пересборки); API остаётся на Render.
5. Аутентификация: Google Identity Services вместо демо-токенов, роли и аудит.
6. Резервные копии, staging-контур, план отката — до первого платящего договора.

### Перенос данных из существующих контуров

Мастер-реестр ≈156 354 `legal_entities` и ≈363 547 строк источников — это
**строки источников, не карточки**. Перенос выполняется как ETL с provenance:

| Источник | Цель | Правило |
| --- | --- | --- |
| `legal_entities` | `legal_entities` | 1:1, сохраняется RUC и источник строки |
| строки источников | `companies` (staging) | только после дедупликации; статус `staging`, не `published` |
| `approved_company_cards_v1` (4 шт.) | `companies` (published) | переносится как есть, с историей подтверждения |
| представления каталога | `search_text_norm` | перестраиваются `reindex_all`, не копируются |

Ничего не удаляется: инвентаризация вместо чистки (§14, Фаза 0).

## 13. Известные ограничения и технический долг

| Ограничение | Влияние | План |
| --- | --- | --- |
| SQLite в разработке | Нет `unaccent`, `tsvector`, PostGIS, полноценных транзакционных блокировок | Переносимая схема + миграции; production на Neon |
| Поиск LIKE по токенам | Нет ранжирования по частотности, нет опечаток, квалификаторы цены не работают | PostgreSQL FTS + `pg_trgm` + словарь запросов |
| Расстояния не считаются | Фильтр «рядом» отсутствует | PostGIS + индекс GiST |
| Демо-токены кабинетов | Не годятся для production | Google Identity + RBAC |
| Нет очереди задач | Переиндексация и ETL — синхронно | Фоновые задачи при объёмах реального каталога |
| Нет выплат | Статус `paid` проставляется вручную | Платёжный контур после Фазы 2 |
| Часы работы — шаблон в JSON | Нет календаря исключений и праздников | Модель расписаний в срезе бронирования |
| Карты — ссылка на внешний сервис | Нет тайлов офлайн | Отдельное решение при пилоте |
