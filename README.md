# PRTDS — Para todos. Para todo.

Цифровая платформа для повседневной жизни в Парагвае: единая точка входа, чтобы
найти товар, компанию или услугу и **сразу перейти к действию** (WhatsApp, звонок,
заявка), а для бизнеса — измеримый канал привлечения покупателей.

Единая концепция проекта: [`docs/prtds-concept-v2.md`](docs/prtds-concept-v2.md)
(рабочая редакция 2.0 от 08.11.2026, полный перенос из `prtds.pdf`).

---

## Что уже построено в этом репозитории

**Срез 1 — сквозной коммерческий путь** (п.2 «Первого конкретного задания команде»
из концепции):

```
поиск → карточка → WhatsApp/заявка → CRM-статус → подтверждённый результат → основание комиссии
```

Путь работает целиком и покрыт тестами (46 проверок):

| Слой | Что сделано |
| --- | --- |
| Каталог | универсальный каталог с **настраиваемым деревом категорий** (46 категорий в демо), филиалы, каналы, товары/услуги, provenance каждого факта |
| Поиск | нечувствительный к акцентам (`movil` → `TecnoMóvil`), мультисловный AND-поиск, синонимы категорий как данные, фильтры по баррио/каналу/цене, сортировки |
| Реклама | платная позиция возвращается **отдельным помеченным блоком** и никогда не занимает место в органической выдаче (§13.4) |
| Воронка | append-only ledger событий с идемпотентностью, дедупликацией, UTM/campaign и словарём «что событие доказывает / чего НЕ доказывает» |
| Заявки | WhatsApp deep-link с предзаполненным сообщением и идентификатором обращения, согласие до передачи контакта, человекочитаемый `ref_code` |
| CRM | статусы и разрешённые переходы, ручная сверка партнёром (реверс отказа допустим с примечанием) |
| Коммерция | контракты, правила комиссии (company > category > global), капы на событие и на период, минимумы, **GMV ≠ выручка PRTDS**, контроль contribution margin |
| Кабинеты | партнёрский (сверка заявок, подтверждение продаж, ликвидaciones) и административный (таксономия, pipeline публикации, аудит) |
| Фронтенд | vanilla ES Modules без сборки, mobile-first, es-PY, PYG без дробных единиц, tz America/Asuncion |
| Языки | переключатель **ES / RU / EN** в шапке каждой страницы; продукт остаётся Spanish-first (§02), RU/EN — языки просмотра для команды и партнёров. Покрытие перевода проверяется скриптом, а не на глаз |

### Чего здесь сознательно нет

- Реальных данных и реальных партнёров: каталог наполнен **вымышленными** компаниями
  Асунсьона для проверки пути. UI и `/api/meta/status` это явно сообщают.
- Интеграций с production из техпаспорта (Neon, Render, Cloudflare, OpenAI, BCP):
  из песочницы разработки нет сети до этих сервисов. См. [`docs/phase0-inventory-checklist.md`](docs/phase0-inventory-checklist.md).
- Модулей лояльности, бронирования, корзины, B2B-закупок, ИИ-чата — это следующие
  срезы (портфель модулей описан в §11 концепции).
- Настоящей аутентификации: в демо — общие токены кабинетов. В production —
  Google Identity Services и разделение ролей.

## Быстрый старт

```bash
# 1. зависимости
python3 -m venv .venv
.venv/bin/pip install -r backend/requirements.txt

# 2. запуск (API + фронтенд одним процессом на 0.0.0.0:8000)
./scripts/dev.sh
```

При первом старте создаётся локальная база и загружается демонстрационный
каталог. Отдельно накатывать миграции для dev не нужно; для production —
обязательно (см. ниже).

| URL | Что это |
| --- | --- |
| `/` | поиск: категории, фильтры, результаты, рекламный блок |
| `/empresa/{slug}` | карточка компании: филиалы, каналы, товары с разбором цены, форма заявки |
| `/solicitud/{ref}` | статус своей заявки (без контактных данных и без денег) |
| `/socio` | кабинет commerce: token `prtds-demo-partner-token` |
| `/admin` | админка: token `prtds-demo-admin-token` |
| `/salud` | честное состояние платформы: что существует, что требует проверки |
| `/docs` | OpenAPI |

Токены партнёров по компаниям (демо): `prtds-socio-nails`, `prtds-socio-rentcar`,
`prtds-socio-kaaguy`, `prtds-socio-almacen`, `prtds-socio-tecnomovil`.
Операционный токен `prtds-demo-partner-token` видит все компании.

### Посмотреть без сервера — офлайн-демо

Если запускать backend неудобно, в репозитории лежит собранное демо:
[`docs/demo/`](docs/demo) — те же страницы (разметка, CSS, JS), но ответы API
записаны заранее, поэтому достаточно открыть `docs/demo/index.html` двойным
кликом. Сервер и интернет не нужны; язык переключается там же, в шапке.

```bash
python scripts/build_offline_demo.py      # пересобрать с живого API
node scripts/check_i18n_coverage.js       # проверить покрытие перевода (нужен jsdom)
```

Ограничение демо: записаны только снятые комбинации фильтров (около 60), поэтому
редкий набор фильтров может показать ближайший записанный результат. На живом
сервере фильтры считаются по-настоящему.

### Языки интерфейса

Испанский — язык по умолчанию и язык продукта (§02 концепции). Русский и
английский добавлены как языки просмотра, чтобы команда и партнёры понимали,
что происходит на экране, не читая по-испански.

Перевод применяется поверх уже отрисованного DOM по словарю «испанский оригинал →
перевод» (`frontend/i18n/translations.jsonl` → `assets/js/i18n-dict.js`): рабочие
экраны при этом не переписываются, а пропуск перевода становится числом, а не
впечатлением. Названия компаний, брендов, баррио, адреса, телефоны, SKU, номера
обращений и коды событий не переводятся намеренно — это данные продавцов и
идентификаторы, а не текст платформы.

## Тесты

```bash
.venv/bin/python -m pytest -q
```

Тесты проверяют не «запускается ли код», а **жёсткие правила концепции**:

- комиссия возникает только при активном договоре → продажа без контракта даёт
  `no_contract_basis` и **0 G.** дохода;
- повторное подтверждение одной продажи не создаёт вторую комиссию (идемпотентность);
- два разных чека — две разные операции;
- отрицательный contribution margin помечается `flagged_negative_cm` и остаётся
  видимым в отдельном поле, а не растворяется в агрегатах;
- капы (на событие и на период) и минимумы договора применяются;
- GMV магазина никогда не выдаётся за выручку PRTDS;
- заявка без согласия → 403; публичный `/api/events` не принимает коммерческие факты;
- карточка в staging недоступна публично, pipeline публикации соблюдает порядок;
- партнёр не видит заявки чужой компании.

## Структура репозитория

```
backend/
  app/
    core/        config, db, ids, money (PYG/bps), text (fold), funnel (словарь событий)
    domain/      models.py (общие сущности), schemas.py (Pydantic DTO)
    modules/     catalog, funnel, leads, commerce  — границы модулей без HTTP
    api/         deps, public, partner, admin      — тонкие HTTP-адаптеры
    seed/        data.py (демо-датасет), loader.py
  migrations/    Alembic: версионированные миграции
frontend/        vanilla ES Modules: страницы + assets/js + assets/css (без сборки)
docs/            концепция, архитектура, чек-лист Фазы 0
tests/           сквозные тесты правил бизнеса
scripts/dev.sh   единая точка запуска
```

Принцип — **modular monolith** (§13.1): один доменный контракт, модули с ясными
границами, HTTP-слой тонкий. Любая новая вертикаль использует общие сущности,
а не заводит свои копии карточек, прайсов и аккаунтов.

## База данных

Локально — SQLite (`backend/data/prtds_dev.db`), потому что в среде разработки
нет PostgreSQL. Схема написана переносимо:

- деньги — **целые гуарани** (PYG без дробных единиц), ставки — **базисные пункты**
  (10 000 bps = 100%), чтобы арифметика была точной на любом диалекте;
- enum'ы — VARCHAR + CHECK (`native_enum=False`), без PostgreSQL-типов ENUM;
- координаты — `Numeric(9,6)/(10,6)`; в production добавляется PostGIS-колонка
  `geography` + GiST-индекс отдельной миграцией (см. `docs/architecture.md`);
- полнотекстовый поиск в production — `unaccent` + `tsvector` (es) + GIN,
  `pg_trgm` для опечаток.

Production-контур:

```bash
export PRTDS_DATABASE_URL="postgresql+psycopg://user:pass@host/db?sslmode=require"
cd backend && alembic upgrade head
```

Миграции: `cd backend && alembic revision --autogenerate -m "…"` → `alembic upgrade head`.
Строка подключения читается из окружения — **учётные данные не хранятся в репозитории**
и не попадают в документы (§13.4).
